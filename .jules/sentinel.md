## 2024-05-25 - [Password Oracle Vulnerability in Registration]
**Vulnerability:** A password oracle vulnerability existed in the user registration endpoint (`/api/v1/auth/register`). The endpoint used `authenticate_user` to check if an email was already taken. Because `authenticate_user` performs a computationally expensive password hash verification, an attacker could observe the timing difference: if the endpoint returned quickly (password mismatch), it indicated the user existed but the provided dummy password was wrong. If it took longer, it either meant the password was right (login successful, user exists) or the user didn't exist at all. Additionally, it caused a bug where a new user trying to register with an existing email but a different password would bypass the "User already exists" check (since `authenticate_user` returned `None`) and trigger a 500 error when the database UNIQUE constraint failed.
**Learning:** `authenticate_user` must strictly be used for login validation. Using functions that perform cryptographic operations simply to check if a user exists leaks information via timing attacks and breaks application logic when the password doesn't match.
**Prevention:** Always use a dedicated existence check function (like `get_user_by_email` which only performs a database lookup) when checking if a user exists to prevent timing attacks and logic errors.
